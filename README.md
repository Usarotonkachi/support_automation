# Ежедневная сводка для support-отдела

Решение тестового задания «Специалист по AI-автоматизации».

Скрипт берёт статусы из CRM и сообщения из рабочих чатов и собирает сводку:
что требует вмешательства, в каком порядке, что подтверждено в CRM, а что
известно только из переписки.

```bash
python3 digest.py data/monday.json      # сводка в консоль
python3 -m unittest -v                  # тесты правил
```

Нужен только Python 3.10+, сторонних библиотек нет.

## 1. Способ обработки

```
CRM + переписка  →  правила по CRM  →  разбор переписки  →  сводка
                    (приоритет)        (дополняет, не подтверждает)
```

Главный принцип: **приоритет и статус определяются только по CRM и времени.**
Переписка не может подтвердить или снять вопрос, она только добавляет
контекст и может поднять приоритет. В сводке это два разных блока:
«Подтверждено в CRM» и «Известно только из переписки».

### Правила по CRM

| Случай | Когда нужно вмешаться | Приоритет |
|---|---|---|
| Оформление | документы не получены | срок сегодня или прошёл — СРОЧНО, завтра — СЕГОДНЯ, позже — ПОД КОНТРОЛЕМ |
| Увольнение | нет подтверждения руководителя | так же, по последнему рабочему дню |
| Поставка карт, «В пути» | плановое время прошло | СЕГОДНЯ |
| Поставка карт, «Принято» | — | действий не нужно |

Внутри одного приоритета случаи сортируются по сроку: что раньше горит,
то выше.

### Правила по переписке

| Сигнал в чате | Что делает скрипт |
|---|---|
| задержка, новое время прибытия | поднимает приоритет доставки до СЕГОДНЯ, даже если срок ещё не наступил; новое время — только «со слов курьера» |
| «карты получили», а в CRM «В пути» | расхождение, СЕГОДНЯ: попросить подтвердить приёмку в CRM |
| недостача, повреждение после «Принято» | СЕГОДНЯ: связаться с получателем |
| «отправил документы руководителю в личку» | пометка: документы ушли в обход рабочего канала, в CRM их нет |
| «руководитель в курсе» | пометка: это слова сотрудника, а не подтверждение руководителя |

Если случай непонятен (неизвестный тип, статус, неполные данные), он не
пропадает, а попадает в сводку с пометкой «разобрать вручную».

### Где нужен ИИ

Для CRM хватает обычных правил: там структурированные поля. Сложность — в
свободном тексте чатов. В прототипе сигналы ищутся по ключевым словам, этого
достаточно для четырёх случаев из задания. На реальных чатах этот шаг
заменяется вызовом ИИ по инструкции из `prompt.md`: модель возвращает те же
сигналы в JSON, а приоритеты по-прежнему считает скрипт. Так ИИ не может
«решить», что вопрос закрыт, — он только читает переписку.

## 2. Сводка по четырём случаям (понедельник, 10:00)

**Начать с С-24**, затем П-08 и С-17. П-09 действий не требует.

| Приоритет | Случай | Почему |
|---|---|---|
| СРОЧНО | С-24 Увольнение | последний день сегодня, нет подтверждения руководителя |
| СЕГОДНЯ | П-08 Поставка карт | срок 10:00 истёк, курьер обещает не раньше 13:00 |
| СЕГОДНЯ | С-17 Оформление | выход завтра, документов в CRM нет |
| ДЕЙСТВИЙ НЕ НУЖНО | П-09 Поставка карт | приёмка подтверждена в CRM |

**С-24. Увольнение — вмешаться сразу.**
- В CRM: последний рабочий день сегодня, подтверждения руководителя нет.
- Только из чата: сотрудник пишет, что руководитель в курсе. Это не подтверждение.
- Проверить: подтверждает ли увольнение сам руководитель.
- Дальше: связаться с руководителем в первой половине дня, зафиксировать
  подтверждение в CRM, убедиться, что закрывающие шаги успеют сегодня.
- Почему первым: срок истекает сегодня, а ответа руководителя придётся ждать.

**П-08. Поставка карт — вмешаться сегодня.**
- В CRM: «В пути», доставка была запланирована до 10:00 — срок истёк.
- Только из чата: курьер задерживается, будет не раньше 13:00. В CRM этого нет.
- Проверить: знает ли точка о переносе.
- Дальше: предупредить точку, обновить время в CRM, в 13:00 проверить статус;
  если не «Принято» — звонить курьеру.

**С-17. Оформление — вмешаться сегодня.**
- В CRM: первый выход завтра, документы ожидаются.
- Только из чата: сотрудник вчера отправил фото документов руководителю в личку.
- Проверить: есть ли документы у руководителя, полный ли комплект, читаемы ли фото.
- Дальше: попросить руководителя переслать документы в канал оформления,
  после получения сменить статус в CRM; если до конца дня документов нет —
  предупредить о риске переноса выхода.

**П-09. Поставка карт — вмешательство не нужно.**
- В CRM: «Принято», приёмка подтверждена сегодня в 09:20.
- Из чата: получатель подтверждает, количество проверено — совпадает с CRM.

Полная сводка в том виде, в котором её увидит сотрудник:
[`output/digest-2026-11-23.md`](output/digest-2026-11-23.md).

## 3. Первый запуск

Скрипт каждое утро получает выгрузку открытых случаев из CRM и сообщения
из рабочих чатов за последние сутки, привязанные к номеру случая, и
отправляет сводку в рабочий чат support-отдела к началу дня. Перед тем как
действовать, сотрудник сверяет пункт сводки с карточкой в CRM и, если
действие опирается на переписку, перечитывает исходное сообщение. Первые
две недели сводка идёт параллельно с ручной работой: сотрудник, как обычно,
составляет список дел сам, а потом сравнивает его со сводкой. Каждое
расхождение — пропущенный случай, лишний пункт или неверный приоритет —
записываем и по нему правим правила. Экономию времени меряем просто:
сколько минут уходило на утренний список до запуска и сколько после.

## 4. Что проверено и что нужно проверить

**Проверено на практике:**
- скрипт на четырёх случаях из задания формирует сводку выше;
- 14 тестов: порядок и приоритеты, CRM и переписка не смешиваются, переписка
  не снижает приоритет, расхождение «получили / в пути», недостача после
  приёмки, задержка до наступления срока, непонятные случаи не теряются.

**Нужно проверить:**
- формат реальной выгрузки CRM и названия статусов — в прототипе они условные;
- как сообщения из чатов привязываются к номеру случая: в задании это дано
  готовым, в жизни это отдельная задача;
- качество разбора переписки через ИИ (`prompt.md`) на реальных сообщениях,
  в прототипе используются ключевые слова, вызов ИИ не подключён;
- регламенты отдела: например, до какого часа нужно подтверждение увольнения
  и что делать, если руководитель не отвечает — сейчас это общие формулировки;
- что сводка не пропускает важные случаи — по итогам двух недель
  параллельной работы.

## 6. Как запустить на своих данных

```bash
python3 digest.py my_cases.json                          # сводка в консоль
python3 digest.py my_cases.json -o digest.md             # сводка в файл
python3 digest.py my_cases.json --now 2026-11-23T10:00   # на заданный момент
```

Если `now` не задан ни в файле, ни через `--now`, берётся текущее время.

Формат входного файла (пример — `data/monday.json`):

```json
{
  "now": "2026-11-23T10:00",
  "cases": [
    {"id": "С-17", "type": "onboarding", "crm": {...}, "chat": [{"role": "employee", "text": "..."}]}
  ]
}
```

| `type` | Поля `crm` |
|---|---|
| `onboarding` — оформление | `first_day` (дата), `documents`: `pending` / `received` |
| `offboarding` — увольнение | `last_day` (дата), `manager_confirmed`: `true` / `false` |
| `card_delivery` — поставка карт | `status`: `in_transit` + `planned_by` (дата и время) или `accepted` + `accepted_at` |

Роли в `chat`: `employee`, `manager`, `courier`, `recipient`. Случай с
неизвестным типом, статусом или неполными данными не теряется: он попадает
в сводку с пометкой «разобрать вручную».
